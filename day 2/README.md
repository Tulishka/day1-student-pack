# ИИ-диспетчер обращений — занятие 2

**Группа C · 120 минут · команды 3–4 человека**

Это дополнительный пакет к вашему проекту первого дня. Распакуйте его **в отдельную папку**, откройте инструкции и продолжайте работу в своей папке проекта. В архиве нет файлов `app.py`, `dispatcher.py` или `static/index.html`, поэтому он не заменит ваш код.

## Цель занятия

Сегодня приложение должно пройти полный путь: **обращение → ответ модели → таблица → ручное исправление**. При исправлении сохраняйте исходное решение модели. К концу занятия обработайте все 12 обращений из `cases_training.json` и запишите минимум два случая, которые стоит обсудить.

## План на 120 минут

| Время | Работа | Проверка |
|---|---|---|
| 0–15 мин | Запустите проект первого дня; распределите роли. | Есть живой ответ API. |
| 15–35 мин | Решите, как в строке хранить исходный и исправленный результаты. | На бумаге или в рабочем листе есть схема строки. |
| 35–75 мин | Добавьте в `static/index.html` изменение категории и приоритета. | Человек может выбрать новое значение, исходный ответ виден. |
| 75–90 мин | Проверьте загрузку и ошибку API. | При ошибке нет ложной строки «успех», кнопка снова доступна. |
| 90–110 мин | Обработайте 12 учебных обращений, сравните с эталоном. | Есть подсчёт совпадений и два разбора ошибок. |
| 110–120 мин | Покажите наставнику два сценария. | Один верный ответ, одно ручное исправление. |

## Роли

- **Интерфейс:** редактируемые поля в таблице, показ исходного ответа.
- **Данные и правила:** сверка 12 примеров с эталонами, поиск спорных случаев.
- **API и логика:** сервер и формат ответа, сообщения об ошибках.
- **Проверка:** контрольные сценарии, заполнение рабочего листа, подсчёт результатов.

В команде из трёх объедините данные с проверкой. Пока один человек работает за компьютером, остальные готовят обращения, проверяют правила и записывают результаты; меняйтесь за компьютером после каждого этапа.

## Задача для интерфейса

В `static/index.html` найдите место, где создаётся новая строка таблицы. Сейчас категория и приоритет выводятся простым текстом. Сделайте для них выпадающие списки с допустимыми значениями. При создании строки сохраните первоначальные `data.category` и `data.priority`; рядом покажите, если пользователь выбрал другое значение. Например: `техника → сеть (исправлено вручную)`.

Исправление должно менять **только строку на странице**. На втором дне не требуется база данных или сохранение после обновления страницы. Используйте `textContent` для текста обращения и ответа модели; не вставляйте их через `innerHTML`.

## Задача для проверки

Откройте `cases_training.json`. Отправьте каждое обращение через страницу один раз и сравните категорию и приоритет с эталоном. Заполните `02_рабочий_лист_команды.md`. Ошибка модели — полезный результат: запишите точный пример, ответ, ожидаемый ответ и возможную причину. Не меняйте эталон задним числом, чтобы улучшить счёт.

## Что показать в конце

1. Запрос, в котором модель предложила категорию и приоритет.
2. Ручное изменение одного значения, при котором видно первоначальное решение модели.
3. Один сбой или неверный формат: приложение показывает ошибку, а не правдоподобный результат.
4. Сколько из 12 категорий и приоритетов совпали с эталоном; два спорных случая.

Подсказки по JavaScript и проверке ошибок находятся в `03_подсказки_по_интерфейсу.md`. На третьем занятии вы получите новый набор обращений для независимой проверки.
